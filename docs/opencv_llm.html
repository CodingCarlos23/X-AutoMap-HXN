What this is: a second way to name materials on OpenCV detections. AutoMap already names each multi-element cluster by matching its element ratios against materials_library.json. OpenCV + LLM sends the same OpenCV blobs, with their measured intensities, to the LLM co-location step the VLM variants use, so library naming and LLM naming can be compared on identical detections. Built in the benchmark as opencv:simple:standard:llm and opencv:simple:raw:llm; Feature Locator option planned.

Workflow: Input to Output

One OpenCV run, two namers. The library path is the existing AutoMap step; the LLM path is new.

How It Works, Step by Step

  1. Detect with OpenCV

    The benchmark runs the real analyze_data_local() on an isolated copy of the TIFFs, twice: standard (normalized + dilated) and raw (no dilation). Every blob lands in MASTER_raw_detections.json with its element, pixel center, radius and the mean / max raw intensity inside it. Local only, no API cost.

  2. Library path (unchanged)

    run_phase_matching() groups blobs of different elements whose centers are within proximity_px, computes element ratios from their mean raw intensity, and scores them against materials_library.json. Result: phase_detections.json, one union box per cluster with its best library match (or "no library match").

  3. Blobs become LLM features

    Every blob, before unions and the intensity filter, becomes a feature: box = center ± radius as fractions of the image (the same format the VLM returns), plus mean_intensity_raw and max_intensity_raw. About 300 blobs over 15 elements for the standard run, a prompt of roughly 6–8k tokens.

  4. Same LLM co-location step as the VLM

    build_colocate_prompt(source="OpenCV") lists each element's features with their intensities and one sentence on reading them (compare within an element; cross-element ratios are rough). query_llm_colocate() is the identical call the VLM variants use: same model, task, schema and output. Only two words differ in the system prompt: "OpenCV-detected" instead of "VLM-detected".

  5. Zones back, normalized

    The LLM returns co-location zones: elements, the intersection box, a best-guess material, self-rated confidence, one-sentence reasoning and up to two alternatives. They are normalized exactly like the VLM zones and saved in the common schema.

  6. Compare

    Level 2 matches library regions against LLM zones (intersection ÷ smaller box ≥ 0.5) and reports region F1, element Jaccard and both names side by side, in the "Library vs LLM on the same OpenCV blobs" table. OpenCV + LLM also appears as a row against every VLM variant, and in Level 3 reconciliation.

Settings

  • vlm.opencv_llm: true in benchmarks/configs/compare_default.json turns it on; it reuses vlm.model and vlm.sample_context.
  • Runs for every OpenCV run (:standard and, with automap_raw, :raw). StarDist is not included yet.
  • Skipped with --no-vlm. API calls appear in the report's "API calls & cost" section under the :llm method names.

Summary

OpenCV + LLM keeps OpenCV's detections and changes only who names the materials. OpenCV finds the blobs exactly as AutoMap always has; instead of only matching element ratios against the materials library, every blob and its measured intensity is handed to the same LLM co-location step the VLM variants use. The LLM decides which elements sit together, draws the intersection box, and returns a best-guess material with its reasoning and the alternatives it would want to rule out.

Because both namers see identical detections, any difference in the report comes from the naming alone, not from detection. That makes it the cleanest test of whether an LLM adds value on top of the deterministic pipeline: where the two agree, where the LLM names something the library cannot, and where they disagree and need checking with another technique. Neither name is an identification; both are hypotheses from XRF element data.
