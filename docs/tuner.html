What it does: start from a sample folder and an initial AutoMap config, run a classical OpenCV detector (no AI / ML models), score the result in code, and let an LLM propose a better config. Repeat for several iterations, saving every one, and keep the best. Finally, run material detection with the best config and compare the materials-library matches with the LLM's own material guesses.

Tuning Loop

The LLM only proposes configs. A fixed scoring function in code decides whether a proposal is better, so the LLM never grades its own work.

How Do We Know It Is Getting Better?

This is the core design question. "The LLM says it improved" is not evidence, so every iteration gets the same score, computed in code. There are no hand labels yet, so the score has two parts that need none:

1 · Injection-recovery (main score)

Plant test particles at positions we choose, run the detector, and score detection F1 against those known positions (IoU ≥ 0.25, as in the benchmark). This makes our own labels; astronomy uses it to tune source detectors on images that have no ground truth.

2 · Proxy score on the real particles

Planted particles cannot show false detections on the real image (boxes on noise, split particles). Measures from the image itself cover that, per element, combined with fixed weights. The LLM sees every part, not just the total, so it knows what to fix.

How the planted particles are made

  1. Find clear particles: run a very strict threshold once per element and keep a handful of bright, isolated particles.
  2. Cut them out with a small margin, so their real shape, size and edge blur are kept (better than synthetic Gaussian blobs).
  3. Paste copies into empty background at random known positions, away from real particles, at 100 %, 50 %, 25 % and 10 % of their brightness. Done in raw TIFF values, before normalization, so planted particles go through exactly the same pipeline as real ones.
  4. Score: F1 on the planted positions, plus the faintest brightness level each config still finds (its sensitivity). New random positions every iteration, with a fixed seed per iteration so runs are reproducible.

Caveat: planted particles are only as realistic as the ones they are cut from, and they sit on clean background, which is easier than crowded regions. That is why the proxy score on the real image stays in the total. Hand labels can replace the injection score later without changing the loop.

Proxy metricWhat it measuresHow it is computed
Signal captured
recall stand-in		Did we box the real signal?Share of significant pixels (above the element's noise floor: median + k·MAD) that fall inside a detection

precision stand-in		Is each box on a real particle, not noise?Mean intensity inside the box vs a background ring around it, as a signal-to-noise ratio; boxes below ~3σ count as false
Split / mergeOne box per particle?Penalty for boxes containing several separate peaks (merged) and for several boxes on one connected blob (split)
StabilityIs this a robust setting or a lucky one?Re-run with each tuned value nudged ±10 %; detection F1 against the un-nudged run. Local CPU only, no API cost

Deliberately not in the score: how many unions match the materials library. Optimizing for that would push detections toward whatever the library contains, and would make the final LLM-vs-library comparison circular.

Samples: Tune Set and Check Set

Each sample is about 14 element TIFFs of the same area. The check set must be data the LLM does not tune on.

SetupCheck setHow good a check
Several samples, same elements (recommended)Whole samples held out: tune on A + B, check on CBest: shows the config works on a different area, not just this one
One sampleHold out ~4 of the 14 elements, mixing strong and weak signalsWeaker: the elements share the same particles, so it mainly tests other signal levels

Planted particles are re-drawn at new positions every iteration, so the LLM cannot learn where they are.

One Iteration, Step by Step

  1. Plant

    Copy every sample's TIFFs and paste the test particles into the copies at this iteration's positions; save the positions to planted.json. The original TIFFs are never changed.

  2. Run

    Write iter_NNN/config.json, run analyze_data_local() on every sample (reusing the benchmark's isolated-copy runner), collect boxes from MASTER_raw_detections.json.

  3. Score

    Compute the score breakdown per element for the tune set and the check set; save scores.json and preview images with boxes.

  4. Ask the LLM

    Send a compact text summary, not images: the tunable part of the current config, the score breakdown per element, per-element image stats (noise floor, peak, typical blob size), and a short history table of earlier iterations. Kept small on purpose (task #6: earlier prompts timed out).

  5. Validate

    The LLM answers with JSON: {"changes": {...}, "reasoning": "...", "expected_effect": "..."}. Code keeps only allowed keys, clamps values to the search-space bounds, rejects configs already tried, and saves the reasoning to rationale.md.

  6. Decide

    Stop at the iteration limit, when the check-set score has not improved for K iterations, or when the API budget is used. Otherwise run the next iteration.

Only classical, non-ML detectors for now. Each key gets bounds in the search-space file.

Final Step: Library vs LLM Materials

After tuning, one run with the best config produces the unions and their element ratios. Two independent namers then label every multi-element union:

Materials library

The existing deterministic match: closest element ratios in materials_library.json, with its confidence. Can only name what is in the library.

LLM

Gets the same elements, ratios and sample context; returns a best guess, self-rated confidence, reasoning and alternatives (the format the benchmark's co-location call already uses).

The comparison lists, per union: agree (same material or family), differ, library only (LLM declined), LLM only (no library match; a hint of what the library is missing). Neither side is ground truth: both are hypotheses from element data, so disagreements are what to check with XANES / XRD / Raman.

Guardrails

  • Code scores, the LLM proposes. The LLM never decides whether its own change helped.
  • Keep the best, not the last. Later iterations can get worse; the winner is the highest check-set score.
  • Check set. Score samples the LLM is not tuning on, so it cannot overfit one image.
  • Small, explained changes. A few keys per iteration, each with reasoning, so the history shows which change caused which effect.
  • Beat a baseline. If random or Bayesian search with the same iteration budget does as well, the LLM is not adding value.
  • Save everything. Prompts, replies, configs and scores for every iteration (the benchmark currently skips the co-location prompt; do not repeat that).

Open Questions

  • Samples: one sample works (hold out elements); 3+ samples with the same elements give a much better check.
  • Score weights: how much injection-recovery vs proxy score; start around 60 / 40 and check it against what looks right by eye.
  • Hand labels: if you find labeled data, it replaces the injection score directly.
  • Scope: start with simple only, or let the LLM switch detection methods too?
  • Intensity filter groups: tune the per-element intensity / offset values as well?
  • Budget: iteration limit, model, and cost cap per run.
